1.3 How the POC-proven behaviours are preserved (contract)

  • Synchronised capture: identical mechanism — server issues capture_at = server_now + 1200 ms; each device corrects by its measured clock offset and fires locally. Target: reproduce 9–148 ms spread on LAN (§8 test).
  • Gated generation: images/edits only (character image as reference), character-lock + anatomy prompt, automated vision gate (same character? exactly 1 head/2 arms/2 legs? pose matches?), regenerate ≤3 attempts, per-step negative prompts where POC needed them (“must NOT stand…”). 11–35 s/image is surfaced as per-step progress.
  • Feedback chain: intent per line → reference exists → alignment, each submission standalone (no history sent), rejected counts toward the (configurable) limit, acceptance regenerates all steps/images and discards the old version.
  • Timings drive async design: ~6 s steps (inline wait), 1–2 min generation and ~10 s/step validation (queued jobs with progress events), voice decision (streaming partials; one-shot fallback ~1.5 s after clip end).
  • Annotation: wonder locates errors → server draws red circles/arrows programmatically on the stored character image (PIL/sharp overlay). AI image-edit annotation is forbidden (POC f: regenerated a different person).

1.4 Local-only deployment & the LAN problem (POC scope)

  • One command starts everything (§3.4): web + API + session service + workers + Mailpit, on this machine.
  • Primary on https://localhost gets camera/mic without warnings. Phones/other laptops on LAN need HTTPS they trust: the dev stack generates a local CA via mkcert (installed once per device) and serves https://<this-pc-lan-ip>. Self-signed without trust, or plain HTTP on a LAN IP, will block cameras — documented as setup step, not discovered by users mid-session.
  • No public exposure: bind to LAN, firewall-friendly single port (reverse proxy in the app server: app, API, WS, Mailpit UI under one origin).
  • Cloud/domain deployment is explicitly out of this design revision; the interfaces (Mailer, storage keys, WS authority) keep it a config move later.

1.5 Mailbox: Google SMTP by config (owner decision)

Decision: Google SMTP is the default mailer, configured — never hard-coded. Anyone cloning the public repo sets their own Gmail address + app password in .env (from the committed .env.example) and OTPs deliver to real inboxes, including testers on other networks. Free at Gmail’s sending limits (~500/day), which is ample for this POC.
  • Config (the public contract): MAILER=gmail · SMTP_HOST=smtp.gmail.com · SMTP_PORT=587 · SMTP_USER=<your gmail> · SMTP_APP_PASSWORD=<16-char app password> · MAIL_FROM="Muse Yoga <your gmail>". Secrets live only in the local .env (gitignored, §3.5); the repo ships names and placeholders, never values.
  • Owner setup (only you can do this): on the sending Google account, enable 2-Step Verification, then create an App Password (Google Account → Security → App passwords) and paste it into your local .env. Never paste it into chat, code, or GitHub — an app password in a public commit must be treated as leaked and revoked.
  • How OTP works: register/login → app generates the code (§2.2) → Mailer.send() sends via Gmail SMTP over STARTTLS → user reads the code in their real inbox (any network). Send failures surface as a designed retry state and are logged without the code.
  • Alternative kept: MAILER=mailpit runs the free local Mailpit inbox (Compose service) for offline development with no Google account — same Mailer interface, config switch only. OTP content, expiry, and rate rules live in business logic (§5), never in the transport.

2  Security

2.1 Threat model (local POC, honest scope)

Assets: OTP codes and login sessions, personal asanas, practice history, the Meta API key, admin authority. Adversaries in local scope: another user/process on the LAN, a stolen logged-in device, credential guessing, malicious uploads, prompt misuse through feedback. Out of scope locally: internet attackers (no public exposure) — but no design choice may make later public deployment unsafe (keys server-side, HTTPS, hashed codes from day one).

2.2 OTP, accounts, and lockouts (scope §5, limits are data)

  • Code: 6 digits from a CSPRNG, 10-minute expiry, single use, stored only as a salted hash (argon2id/SHA-256+salt for a 6-digit code with attempt caps), compared in constant time. Plaintext codes exist only in the outgoing email and server memory during send.
  • Registration: max 3 code requests per email lifetime — counter on the registration record, incremented atomically before sending; the 4th request is refused and the email is marked permanently blocked. No recovery path exists in code or UI.
  • Login: 3 failed verifications → 6-hour lock (timestamp on account); a second lock event → permanent block. Counters reset only on successful login before any lock. All limits read from the settings table (§7) so admin changes apply without deploys.
  • Anti-enumeration: identical responses for unknown/blocked/locked emails (“If this email can sign in, a code is on its way” + the specific state only after a code attempt where scope requires the message); per-IP and per-email send throttles; CAPTCHA deferred (local POC) but throttle hooks are in the API layer.
  • Sessions: opaque 256-bit session tokens, hashed at rest, HttpOnly; Secure; SameSite=Lax cookies, 30-day idle expiry, per-device session rows enforcing the max-3-devices login rule — a 4th login is refused with scope’s exact logout-first message, never by silently evicting another device.

2.3 Authorisation (every endpoint, no exceptions)

  • Server middleware resolves session → user → role (admin iff email ∈ config file, read at startup + file-watch reload; changes audited).
  • Personal asanas, favourites, history: owner check in the service layer on every read/write (IDOR-safe: foreign IDs return 404).
  • Admin-only: approvals/rejections, public enable/disable, character & PDF uploads, limits. Rejection requires a non-empty reason (DB check constraint, §7).
  • Practice sessions: join requires the session code and a login session for the same user as the creator (A3); a different account with the code gets nothing.

2.4 The never-stored guarantee (photos + voice audio)

  • Camera frames for validation: browser memory (Blob) → TLS to server memory → Meta API → references dropped. No disk write, no object storage, no DB column, no log field, no analytics event can carry image/audio bytes — enforced by type (upload handlers accept bytes only into the validation/transcription functions) and by a CI grep test over storage modules.
  • Voice audio: Primary mic → PCM chunks streamed through the server proxy → Meta realtime WS → transcript only. Server forwards bytes without buffering to disk; transcripts are kept only as the matched phrase + decision in session state, then discarded. Session logs record timings and decisions, never transcripts beyond the POC page’s local display.
  • Mic/camera indicators are UI-truthful: mic track exists only inside the Listening window; framing analysis never leaves the device.

2.5 Backend services cannot be reached — or run — directly (owner question)

The rule: a logged-in browser can ask the API for an outcome; it can never invoke a backend service, worker, database, or external API itself. Login changes which API outcomes a user may request, never what network things they can touch.

LayerReachable from browser/LAN?How it is enforced
Web app + API + session WS (one origin)Yes — the only exposed surfaceSingle local port behind the app reverse proxy; everything else 404s. Same-origin only (CORS denies other origins; WebSocket upgrade checks Origin + session cookie).
Domain/business-logic modulesNo listener existsThey are in-process libraries inside the server (modular monolith, §6), not services with ports. There is no URL, socket, or command a user — logged in or not — can address them with. Only API handlers call them, after auth.
Job workers (generation, validation, PDF)NoWorkers poll the internal Redis queue; they expose no HTTP. Users can only create a job request through an authorised API action (e.g. “Create Asana”), which the server validates (role, ownership, quotas, state) before enqueueing. No endpoint accepts a job type, payload, or Meta prompt from the client.
PostgreSQL / RedisNoBound to the internal Docker network only (no host port published in the shipped Compose file; a localhost-only debug mapping is off by default). Credentials exist only in the server’s .env; the browser never receives them.
Meta APIs / Gmail SMTPNoKeys/passwords live server-side (§2.6). The browser cannot call Meta with our key, cannot send mail, and cannot even learn the endpoints’ credentials from responses or errors (sanitised error mapping at the API edge).
Admin operationsAPI-shaped onlyApprove/reject/limits/uploads are ordinary API routes plus the admin-role check (§2.3) and audit. There is no admin console port, CLI-over-HTTP, or debug endpoint in the shipped build (/health returns reachability booleans only, no data).
  • Authorisation is per-operation, not per-login: every handler re-derives “may this user do this action on this object now?” (owner/admin/state/quota checks in the domain layer, §5). A valid session cookie alone authorises nothing beyond identity — replaying a captured request for someone else’s asana, an approval, or a second device-join fails those checks (foreign IDs 404; role failures 403; both audited).
  • Cookie-session hardening for mutations: SameSite=Lax + CSRF token on state-changing requests, so another LAN site cannot ride a logged-in browser; WebSocket messages are schema-validated and state-machine-checked (a client cannot fabricate a captureAt, verdict, or role change — the server originates all of them).
  • Rate and abuse limits at the edge: per-session/per-IP throttles on OTP, creation, feedback, and voice windows, so “logged in” cannot become “unlimited AI spend” (§6.2 cost log + caps).
  • Later, if services are ever split: this design’s module seams become internal-only listeners on a private network with a shared service secret/mTLS — the browser-facing API surface does not grow. That is a deployment change, not a redesign.

2.6 Uploads, secrets, and audit

  • Uploads (PDF, character images): extension + magic-byte validation, size caps (PDF 50 MB, image 10 MB), random storage keys (no user filenames in paths), PDF parsed in a sandboxed worker, images re-encoded before storage. No SVG, no archives.
  • Secrets: Meta key + optional Gmail app password only in server .env (gitignored); config file lists the admin email only. Keys never reach the browser, logs, or error messages.
  • Audit log (append-only table): admin approve/reject (with reason), limit changes, config reloads, OTP lock/block events, session create/end. No user content in audit rows.

4  Front end

4.1 Routing & navigation

  • Routes mirror the site map (gate/§ prototype): /login /register /public /personal /detail/:id /favourites /create /history /practice/* /admin. Unauthenticated → /login for every route (scope: nothing browsable logged-out).
  • Origin-aware stack (C13): an explicit in-app history carrying origin (public|personal|favourites|detail); Detail’s back and practice End/Practice-Again return through it, never bare links.
  • Global header on all screens except coaching (C9); coaching keeps its slim strip (app name left, asana centred, step chips right).

4.2 Components & layout contracts

  • Shared asana card (C12) — one component; props = asana + state (active|disabled|pending|rejected|public); personal-only actions render from state, layout identical across libraries.
  • No-scroll system (C10): each route owns a viewport budget (CSS grid rows: header / content / pager). Libraries & history paginate (6/page as prototype), admin tables paginate, step lists in Detail use internal two-column fit. A route that cannot fit fails its layout test rather than scrolling.
  • Distance readability: count numerals in Fraunces at clamp(54px,10vh,82px), verdicts and “Listening” at poster size, text only on solid/backed surfaces over imagery (prototype v5–v6 lesson, carried as a lint-checked class).
  • Accessibility: focus-visible states, prefers-reduced-motion, aria-live for spoken-equivalent status (count, listening, verdict), colour never the only signal (icons + words for every state, P6).

4.3 Camera, microphone, and media

  • Explicit Enable Camera / Enable Microphone buttons with plain-language status (not started / on / blocked — …) — never silent autoplay (POC lesson). Denied mic → voice unavailable notice; the session still starts from the Start screen and each timeout path explains the mic state there (no in-coaching tap exists).
  • Own camera via getUserMedia; capture frames drawn to canvas → JPEG Blob in memory. Other-device live video via WebRTC (A1); if a peer stream fails, that tile degrades to the last-capture thumbnail (POC-proven) and says so.
  • Framing (A9): MediaPipe Pose per camera, on-device; badge per tile (IN VIEW ✓ / NOT FULLY IN VIEW ⚠); losing framing on any camera pauses counting (Framing Warning, C5).
  • Voice capture: AudioContext + AudioWorklet → 16 kHz PCM chunks → WS to server proxy → Meta realtime. Listening opens only after the TTS prompt’s onend; a visible countdown ring (10 s) and mic-live indicator run only inside the window.

4.4 Practice front-end state machine

The browser renders session state; it does not own it. The session service (§6) is authoritative; every device renders the same broadcast state. Local optimistic UI is limited to camera/mic previews.

SETUP → DISCLAIMER → [SELECT if generic] → START (demo/skip + Start)
  → per step: INTRO → FRAMING → VOICE_PROMPT → LISTENING ─heard→ COUNT×3 ─→ next INTRO
                                   LISTENING ─10s/error→ (apology spoken) → START (same step pending)
                                   FRAMING lost ─→ WARNING ─all-in-view→ VOICE_PROMPT
  → ANALYSING → RESULTS → (Practice Again → START, same asana) / (Pick Another → SELECT → DISCLAIMER → START)
  • Demo playback is server-sequenced (A8): step index broadcasts on narration end + ~2 s hold; Pause / Hear Again / End Demo are Primary-issued session commands, rendered identically on Secondaries.
  • Role switch (C2): Secondary button sends a switch request; pre-capture it applies at once, mid-step it renders “Primary after this step” and applies at the step boundary (new Primary speaks the next step).
  • Disconnect: presence loss renders the offline banner + tile replacement on all devices; the announcement is spoken on the (possibly newly promoted) Primary.

4.5 Creation, libraries, history, admin (front end)

  • Creation wizard (6 steps as prototype): checks → steps review (read-only) → generation progress per step (stage + elapsed) → review + feedback (remaining count, rejection reason inline) → accept. Long waits offer “keep this tab open” + job polling; closing the tab does not cancel the server job, re-entering resumes its status.
  • Search is diacritics-insensitive in the UI (normalised index from server, A4): Vrikshasana finds Vṛkṣāsana.
  • History: month calendar (dots + counts), day list, session detail = stored Results content. No user photo can render here — the API has no field for one.
  • Admin: five tabs as wireframed; rejection reason is a required field client- and server-side; limits form edits settings (§7) with audit.

5  Business-logic layer

packages/domain — pure TypeScript functions over data passed in, no I/O, no framework. Every scope rule lives here exactly once and is unit-tested here; API, workers, and the session service call it. If a rule cannot be written as a pure function with tests, it does not ship.

                  deviceOffline{id} · framing{deviceId,inView} · analysing{step} · results{...}
  • Snapshots on join/reconnect (state is server-owned; a refreshed device re-renders, never forks the session).
  • Heartbeats 5 s; two misses = offline event + spoken announcement; capture sets exclude offline devices from that set onward.
  • Clock sync: ping/pong offset estimation at join and per step (POC method); captureAt scheduled +1200 ms out.
  • WebRTC signalling rides the same WS (rtc{offer|answer|ice} relay); media never touches the server.

6.2 Background jobs

  • Redis lists + worker loops with a jobs table for status (queued|running|done|failed, per-step progress JSON), so waiting UIs poll/stream real stage + elapsed instead of spinners.
  • Job types: pdf.parse · creation.steps · creation.image(step) · creation.regenerate · validation.step · annotation.render. Voice streaming is not a job (it is a live proxy); one-shot transcription fallback is a request, not a queue.
  • AI cost/rate controls: per-user concurrent-job cap (1 creation at a time), attempt budgets in domain rules, every Meta call logged (model, duration, est. cost) to the AI-call log — the production successor of the POC ledger/guard.
  • Failure semantics: a failed generation step fails the job with a retry action and saves nothing; a failed validation step retries once, then reports that step as “could not check” rather than guessing (owner-visible, never silent).

6.3 Observability

Structured server logs (session id, step, decision, ms timings; no content bytes), a local /health page (DB/Redis/SMTP/Meta reachability), and per-session timing records reproducing POC metrics (capture spread computed from device fire-times, voice decision latency, validation seconds/step) so §8 acceptance numbers come from the app itself.

8.4 Acceptance tests the build must pass (evidence, not claims)

  1. Sync: 3 real devices (2 laptops + phone) on LAN — capture spread measured from device fire-times; PASS = same order as POC (≤~150 ms), disconnect announced, thumbnail fallback exercised by disabling WebRTC.
  2. Voice: at 5 ft, quiet room: 10 trials each phrase (3 accepted → start; “already/not ready”/silence → apology + Start screen); streaming decision latency recorded; one-shot fallback forced and re-tested.
  3. Framing (A9 gate for C5): step out of each camera in turn → pause within ~1 s, no capture counted; return → automatic recount; false-pause rate noted for owner.
  4. Generation: one new asana end-to-end — steps ~seconds, images gated (gate log per step), no text-only fallback in ai_calls; feedback rejection shows reason and decrements remaining count.
  5. Rules: domain unit tests for OTP lifetimes/locks, device cap, publication guards, feedback counting; API tests for owner/admin authorisation on every route; schema allowlist test (no photo/audio fields).
  6. Privacy: after a full session, inspect DB + data/: only text + annotated character images exist; server logs contain no transcript/image bytes.
