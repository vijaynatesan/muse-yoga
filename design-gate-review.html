1  Disposition for every scope change

“Accept” means: write it into a scope revision in design.MD. “Revert” would mean: change the UI back to scope.MD before designing. One line of reasoning each.

  1. C1 — First device is AUTO-Primary. Accept · provisional Owner-directed; keep role assignment as a server-side switch (“auto-first” vs “first-claim”) so reverting after user testing costs no protocol change.
  2. C2 — [Make This Device Primary] on every Secondary, queued mid-capture. Accept Scope §13.1 already gives the tap; queuing to the step boundary only stops a capture set being split across two speaking Primaries.
  3. C3 — Auto-promotion if the Primary leaves pre-session. Accept Scope is silent, and C1 deadlocks without a promotion rule.
  4. C4 — Demo Offer → Demo Playback → Ready Gate before any capture. Accept It does not change the §13.3 script; it only makes Ready the sole entry to it, so selecting an asana never starts counting.
  5. C5 — Out-of-frame detection & Framing Warning (pause/resume). Accept · conditional It closes the “pose cannot be measured” case, but design must prove on-device detection without storing photos — or flag it back (assumption A9).
  6. C6 — Explicit “Select Asana” step, two entry orders. Accept Scope assumes an asana is already chosen; this makes the generic entry workable and gives pre-selected arrivals a confirm-or-switch point.
  7. C7 — Per-asana contraindications inside the Disclaimer. Accept It discharges §13.4 properly; a generic-only acknowledgement would be uninformed.
  8. C8 — Clickable Results steps → large annotated view. Accept §14.2 already requires the annotated character image per step; the modal is presentation and stays on programmatic overlay, never AI image-editing.
  9. C9 — Global header on every screen except coaching. Accept Branding and shell only; coaching keeps its slim strip and stays readable at a distance.
  10. C10 — No scroll, anywhere. Accept Owner hard rule; meet it with viewport budgets and pagination for libraries, history, and admin — not by shrinking or hiding essentials.
  11. C11 — Coaching layout: equal split, minimal at all times. Accept Direct layout reading of §13.2 (own body vs. stored target as equal halves, secondaries as a small strip) with the same layout between steps as in pose.
  12. C12 — Public / Personal / Favourites share one card grammar. Accept Identical asana identity across §§11–12, with personal-only actions as state-driven additions, not a second layout.
  13. C13 — Origin-aware back navigation everywhere. Accept No scope rule forbids it, and bare links would lose the library the user came from.
  14. C14 — Disclaimer/selection state is never silently reused. Accept Safety invariant: a new asana invalidates the old highlight, caution box, and checkbox.
  15. C15 — Voice “Ready” gate before every step (new, this request). Accept · corrected 2026-10-31 There is only one click in the whole practice flow — Start on the demo / skip-demo Start screen. After that click, every step starts by voice alone. A timeout returns to that same Start screen (see §4); there is no per-step click. Creates a new to-prove assumption A10.
Net result if you approve as proposed: C1–C14 all accepted (C1 provisional, C5 conditional), plus C15. Nothing is reverted to scope as written, and nothing is dropped silently.

2  Contradictions beyond the C-list

Between scope.MD and uidesign.MD, not already recorded in UItoDesignHandoff.MD §2:

  1. Mobile Secondary drops the other-device feeds. Scope §13.2 requires every device to show the other devices’ live feeds; uidesign §3.9 omits them on mobile Secondary (owner question Q3). C11 covers the Primary layout, not this per-device exception.
  2. Camera-less Primary. Scope §13.1 says the Primary “has audio and also captures photos” and §14.1 defines a set as one photo per device, yet uidesign §3.11b lets the Primary “Continue without this camera” before Step 1 (Q4). That changes what a validation set contains.
  3. Step list reduced to a number strip. Scope §13.2 requires “the list of all steps … with the current step highlighted”; uidesign §3.6 renders a one-row number strip plus an instruction panel (Q2). C11 is about split sizing, not this reading of “list.”
  4. Practice Again skips the Disclaimer. Scope §13.4 requires the disclaimer “before a practice session begins,” but uidesign §7 returns Practice Again straight to the Ready Gate with no new disclaimer. C6 covers first entry and reselect; the redo case needs a “same session vs. new session” ruling.

No further contradictions found. The remaining shared rules (redo all steps, no score, disable-only deletion, whole-asana regeneration on accepted feedback) agree in both documents.

Layer by layer — what each part does, and why this choice

1

Devices — Primary speaks and listens, Secondaries only watch and film

  • Primary: TTS announcements, microphone (C15 window only), camera.
  • Secondaries: camera only, muted, no mic — scope §13.1 unchanged.
  • Live video between devices uses WebRTC; the session service only introduces the devices to each other.
2

Browser app — React + Vite, TypeScript

  • All screens from the approved prototype, rebuilt properly (prototype code is throwaway).
  • No-scroll contract: every screen fits the viewport; long lists paginate (C10).
  • Camera frames for framing (MediaPipe Pose) are checked on the device and thrown away — checking never uploads a photo.
  • Photos for validation are held as in-memory blobs and discarded after the result.
3

Session service — the single clock and referee for practice

  • Owns the state machine: Setup → Disclaimer → Start screen → per-step Intro → Framing → Voice/Listening → Counting/Capture → … → Analysing → Results. Listening timeout returns to the Start screen; there is no per-step click state.
  • Capture is scheduled at a server timestamp (+1200 ms lead) with per-device clock correction — the exact POC mechanism.
  • Role switches (C2) take effect at step boundaries; disconnects are detected by heartbeat and announced on the Primary.
4

API + business rules — Fastify services, rules written once as testable logic

  • Auth/OTP, device limit, libraries, publication workflow, favourites, history, admin limits.
  • Limits (feedback 3, OTP 3, lock 6 h, devices 3) are data an admin can change, not code constants.
  • Every rule is enforced on the server; the browser only displays the outcome.
5

Background jobs — anything slow never blocks a screen

  • Reference-PDF parsing after upload (status: Processing / Ready / Failed).
  • Asana creation: steps, then one gated image per step, with per-step progress to the waiting UI.
  • Pose validation after the final step (~10 s/step), then programmatic annotation.
  • Voice transcription during the 10 s Listening window, streamed so “Ready” is acted on at once.
6

Data — PostgreSQL for facts, object storage for files

  • PostgreSQL: users, OTP counters, asanas, steps, favourites, sessions, history text.
  • Object storage: characters, stored step images (written once, read every session, never regenerated), annotated images, uploaded PDFs.
  • Deliberately absent: no table or bucket for user photos or voice audio — history holds text + annotated character images only.

Two journeys through the diagram

Practice: Start screen (demo / skip demo) — user clicks Start once → Step 1: framing OK → “Say Ready…” → voice “Ready” (or 10 s pass → apology → back to the Start screen; clicking Start there returns to the same step and asks by voice again) → capture-at timestamp to all devices → 3 sets, 3 s apart → next step asks by voice again, no click → …final step… → validation jobs → Results spoken + history saved (text + annotated character images only).
Create an asana: Name + character → reference & duplicate checks → wonder writes steps (~6 s) → you review steps → image jobs, one per step, each vision-gated (1–2 min, progress shown) → you review, optionally feedback (checks → whole asana regenerated) → Accept saves images once, forever.

How each POC-proven behaviour survives this stack

  • Synchronised capture (9–148 ms, 3 devices): same mechanism, not a new invention — server timestamp + clock-offset correction, now inside the session service.
  • Gated image generation (11–35 s/image): images/edits with the character image only, character-lock + anatomy prompts, vision gate after every image, regenerate on failure (max 3). Never a text-only fallback.
  • Feedback chain: intent (line by line) → reference exists → alignment, each submission standalone, rejected attempts count toward the limit, acceptance regenerates everything.
  • Observed timings (~6 s steps, ~10 s/step validation, 1–2 min creation): the reason creation and validation are queued jobs with honest per-step progress instead of spinners or blocking requests.
  • New and unproven (flagged, not hidden): WebRTC live feeds (A1) fall back to POC-proven capture thumbnails; voice transcription (A10), when not heard, returns to the existing Start screen — there is no per-step click fallback.

4  New feature C15 — voice “Ready” gate (practice session only)

Your specification, restated precisely so design.MD can implement exactly this. Defaults I have chosen where you were silent are marked DEFAULT and collected as questions in §5.

Where it sits — one click in the whole flow, then voice only

There is exactly one click: Start on the Start screen — the screen where you choose to watch the demo or skip it and start the asana. Clicking Start enters coaching. From then on, every step, including Step 1, starts by voice alone. There is no per-step click, button, or tap anywhere in coaching. Sequence for Step 1: click Start → walk to the mat → get into position → say “Ready” → counting begins. Later steps never return to a button; each one asks by voice again.

Correction (2026-10-31): an earlier draft of this page invented a per-step “Click-to-Start gate.” That does not exist and has been removed everywhere. The timeout path returns to the existing Start screen, as specified below.

Per-step sequence (replaces nothing after counting starts)

S1 Step intro. Primary speaks “Step N” + the full instruction (as today). → Framing check. Counting cannot be armed until every camera reports fully-in-view (C5). If not, the Framing Warning speaks instead and no listening starts. → Voice prompt. Primary speaks: “Say ‘Ready’ when you are in position.” Only when that speech has finished does listening open — so the app never transcribes its own voice. → LISTENING (max 10 s). Primary microphone only; Secondaries stay muted and mic-less (scope §13.1). Screen shows a large “Listening… say Ready” state with a 10-second countdown ring. Recognition switches off immediately when “Ready” is heard, when 10 s elapse, or on any error. → Heard “Ready” → proceed at once to “Get ready — 1, 2, 3,” captures ×3, exactly as scope §13.3. · Not heard → Primary speaks: “Sorry, I didn’t hear you say Ready. Click Start when you want to start.” Recognition is already off. The app goes back to the Start screen (the demo / skip-demo screen with the Start click). No counting happens there.

Timeout — back to the Start screen (no per-step click exists)

  • The app returns to the existing Start screen — where the user can see the demo or skip it and click Start. It does not create a new screen, and coaching gains no button.
  • Progress is kept: completed steps stay completed, valid captured sets stay filled, and the pending step stays pending. Returning does not restart the asana and does not skip the step.
  • Clicking Start there re-enters coaching at the same pending step and runs the voice prompt for that step again (“Step N” → framing → “Say ‘Ready’…”). The click itself never starts counting — after the click, the step still needs the spoken “Ready,” exactly like every other step.
  • So the click has one job only, at the Start screen: enter (or re-enter) coaching. Inside coaching, voice is the only start signal, for every step.

Recognition mechanics (what design must build)

  • Primary-only microphone via getUserMedia, with an explicit Enable Microphone step alongside Enable Camera in Device Setup, and the same plain-language blocked state if permission is denied. Denied or failing mic follows the same path as a timeout — apology, back to the Start screen with the reason shown there — so the user can fix the mic and click Start to try voice again. There is no tap that bypasses voice inside coaching.
  • API: Muse Voice Transcribe API with the same project API key, called only from the backend (key never in the browser). The browser streams short audio chunks during the 10 s window; the backend returns a transcript decision as soon as the word is recognised, so “Ready” at second 2 does not wait until second 10.
  • Match rule (DECIDED, extended 2026-10-31): accepted phrases are “ready”, “I’m ready”, and “let us start” (plus “let’s start / I am ready”), matched as whole word tokens — “already” and “not ready” must not match. Any other speech, noise, or silence counts as not heard. The Primary’s own prompt cannot trigger it, because listening opens only after speech ends. A quick POC now exists at POC/g_voice/ (see §4 note below).
  • Privacy, structurally: audio lives in memory only, is sent only for this transcription, and is discarded with the transcript as soon as the step starts or times out — the same guarantee as camera photos (never stored, never logged, never in history). A persistent “Microphone is off except when you see Listening” indicator makes this visible.
  • Multi-device sync: the listen / heard / timeout decision is a session event broadcast by the session service, so every device shows Listening, then counting — or the return to the Start screen — at the same moment. Captures remain synchronised by the proven server-timestamp mechanism; voice only decides when the next capture schedule is issued.
  • Framing interaction: if framing is lost while listening, listening cancels, the Framing Warning speaks, and the voice prompt repeats once framing is restored. A half-heard “Ready” never starts a step.
Honesty flag — new assumption A10 (TO-PROVE). The POC never called the transcription API: the POC report (POC/POC_REPORT.md §g) records only that a transcribe/ASR model exists in the Meta catalog, which is why browser TTS was chosen for speaking. Endpoint shape, streaming support, word-level latency, accuracy at 2–3 m from a laptop/phone mic, and cost per step are all unproven. design.MD must therefore specify: streaming or short-chunk transcription with a decision in ~1–2 s of the word being spoken (a single 10 s file upload after the window would make “Ready” feel broken), far-field accuracy evidence, and the return-to-Start-screen path as the designed behaviour whenever transcription is slow, unavailable, or wrong — re-entering by the Start click and asking by voice again, never a per-step tap.
POC g result (2026-10-31, POC/g_voice/): the same API key works with muse-voice-transcribe-1.0. Synthesized clips through the real server + API: “ready”, “I am ready” (heard as “Hi I’m ready”), and “let us start” all matched; “already”, “not ready”, and silence correctly did not. One-shot API time ~1.4–1.6 s after the clip ends, ~$0.00005 per attempt. Still unproven: human voice at 2–3 m and streaming latency — try it yourself: python3 POC/g_voice/server.py 5174 → http://localhost:5174/.

Effect on the session state machine

CAPTURING gains, per step: INTRO → FRAMING_CHECK → VOICE_PROMPT → LISTENING (≤10 s) → COUNT×3, with LISTENING —timeout/error→ START_SCREEN —Start click→ (same step) INTRO and LISTENING —framing lost→ FRAMING_WARNING → VOICE_PROMPT. The Start screen is the only click in the flow; Analysing and Results are unchanged. C15 touches C4 (the Start screen remains the session door, for first entry and for timeout re-entry alike), C5 (framing gates the prompt), and A2 (the prompt and the apology are Primary TTS lines).
